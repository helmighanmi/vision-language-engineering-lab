## 3. Issues found (fix before merge)

### High — can break CI / local development

#### 3.1 `[tool.uv] conflicts` is likely an invalid pyproject key (`pyproject.toml`)

```toml
[tool.uv]
default-groups = ["dev"]
conflicts = [[{ extra = "local" }, { extra = "cpu" }]]
```

`conflicts` is not a documented `[tool.uv]` key in uv (conflicts live in `uv.lock`, generated by `uv lock`). `uv sync` may error on an unknown key or silently ignore it, which means the CPU/local extra isolation is not actually enforced in pyproject. The lock file already carries the conflict, so `uv sync --frozen` may still work, but this key is suspicious.

**Fix:** Remove the `conflicts = ...` line from `[tool.uv]`; keep the lock-file constraint. Verify with `uv sync --frozen --no-dev --extra cpu` and `uv sync --frozen --no-dev --extra local` after the change.

#### 3.2 Dead / misleading env var in `docker-compose.cpu.yml` (`api` service)

```yaml
NUEXTRACT_MAX_OUTPUT_TOKENS: ${NUEXTRACT_MAX_OUTPUT_TOKENS:-4096}
```

`Settings` has `local_max_output_tokens` (env `NUEXTRACT_LOCAL_MAX_OUTPUT_TOKENS`), not `max_output_tokens`. pydantic-settings ignores unknown env vars, so this Compose variable has **no effect**. The cap still comes from code default (4096), so behaviour is coincidentally correct, but the variable is dead and confusing — and if someone changes it expecting an effect, nothing happens.

**Fix:** Rename to `NUEXTRACT_LOCAL_MAX_OUTPUT_TOKENS` in `docker-compose.cpu.yml` (and `.env.example` already documents the correct name).

### Medium — correctness / observability

#### 3.3 `/ready` reports a misleading `device` for remote backends (`api/routes/health.py`)

```python
device=getattr(info, "device", None) or runtime.device,
```

For `VLLMClient` / `OllamaClient`, `info.device` is `None`, so it falls back to `detect_runtime()` — i.e. the **local machine's torch device** (e.g. `cuda` on a GPU box even when serving via remote vLLM, or `cpu` on a laptop hitting Ollama). The field is ambiguous: is it the backend device or the local device?

**Fix:** Report `device` only when the backend provides it; otherwise `null`. Document the semantics in `docs/cpu.md` or the API docs.

#### 3.4 Ollama health can return `True` with zero models (`core/client.py`, `OllamaClient.health`)

```python
if not models:
    return True
```

If Ollama is reachable but has no models pulled, `/ready` reports ready; extraction then fails with a 404. The "model missing" warning path exists, but the empty-list short-circuit defeats it.

**Fix:** Return `False` (or at least not `True`) when `models` is empty, so `/ready` accurately reflects readiness.

#### 3.5 `AutoClient._probe` treats any HTTP < 500 as "server reachable"

```python
response = await probe.get(url, headers=headers)
return response.status_code < 500
```

A 401/404 from an unrelated service on port 8000 would cause AutoClient to bind to `VLLMClient`, then fail on generate. The vLLM probe hits `/models`, which is reasonable, but a 404 shouldn't count as reachable.

**Fix:** Require a successful status (e.g. `200 <= status < 400`) for the vLLM probe, or probe `/v1/models` specifically.

#### 3.6 Non-standard Ollama message roles depend on the official Modelfile (`core/client.py`, `OllamaClient._messages`)

Ollama receives roles `template`, `instructions`, `mode` (not standard `system`/`user`). The PR notes this "follows the official Modelfile contract" and is covered by mocked tests, but **real CPU inference was not run in CI** (no model weights). If the official `numind/nuextract3` Modelfile doesn't map those roles as expected, extraction will silently return garbage or errors.

**Fix:** Add an integration/smoke test that runs against a real Ollama instance (gated behind an env var so it's opt-in in CI), and document the exact Modelfile dependency.

### Low — documentation & polish

#### 3.7 CPU Docker image docs promise Streamlit at 8501, but the image only runs uvicorn (`docker/Dockerfile.cpu`, `README.md`)

`Dockerfile.cpu` `CMD` is `uvicorn nuextract_app.api.main:app ...` on port 8080. Nothing listens on 8501, yet the README says:

```
docker run ... nuextract3-studio:cpu
# Then open http://localhost:8501 (demo)
```

**Fix:** Either (a) add Streamlit to the CPU image CMD (entrypoint script launching both uvicorn and streamlit), or (b) correct the README to say the CPU image exposes only the API (8080) and use `docker-compose.cpu.yml` for the full UI stack.

#### 3.8 `README.md` Python version inconsistency (pre-existing, touched by this PR)

README says "Python **3.11 / 3.12**" while `pyproject.toml` `requires-python = ">=3.11,<3.14"`. Minor; align when touching this section anyway.

#### 3.9 `docker-compose.cpu.yml` pins `ollama/ollama:latest` and no version pin for the API image in the overlay

Production guidance elsewhere says pin the vLLM base image; CPU path uses `latest` for Ollama. Not blocking, but worth a note in `docs/cpu.md` about pinning for prod.

#### 3.10 `cli.py` health output no longer shows the configured base URL

It now prints `info.endpoint` ("in-process" for Transformers). Cosmetic only; fine.

## 4. Security notes

| Item | Assessment |
|------|------------|
| `trust_remote_code=True` default (`config.py`) | The Transformers backend loads `numind/NuExtract3` from Hugging Face with `trust_remote_code=True`. This executes arbitrary code from the model repo. There is a repo decision doc (`docs/decisions/003-trust-remote-code.md`) showing the team has considered this. Keep, but document the supply-chain implication in `docs/cpu.md` and consider making it opt-in for high-security environments. |
| `model_api_key=EMPTY` sent to Ollama | Harmless; Ollama ignores auth on `/api/tags` and `/v1/chat/completions` by default. |
| No secrets introduced | All new env vars are non-secret. |
